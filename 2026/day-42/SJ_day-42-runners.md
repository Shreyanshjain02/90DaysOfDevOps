### Task 6: GitHub-Hosted vs Self-Hosted
Fill this in your notes:

| | GitHub-Hosted | Self-Hosted |
|---|---|---|
| Who manages it? | ? | ? |
| Cost | ? | ? |
| Pre-installed tools | ? | ? |
| Good for | ? | ? |
| Security concern | ? | ? |


Github-hosted:
- Github manages all runners
- Billed for private repo,  free for public repositories.
- Comes with a vast library of pre-installed software (Docker, CLI tools, etc
- Good for practicing and Teams wanting zero maintenance, quick setup, and automatic scaling.
- jobs run in clean, ephemeral VMs that are destroyed after use, minimizing cross-job risks
Self-Hosted:
- machine owner manage the infrastructure, OS, security patches, and runner application.
- Cost of machine and running jobs are free
- machine owner manage all installation and pre-requisites
- Projects requiring custom hardware, access to internal networks, or specific OS versions. who want more secure and controlled environment.
- Risks from untrusted code (especially in public forks) persisting on the machine and access to your internal network. Source code leakage.

## Hints
- Runner setup script is generated by GitHub — just copy and run it
- Self-hosted runner runs as a background service: `./run.sh`
- To run as a service (persistent): `sudo ./svc.sh install && sudo ./svc.sh start`
- `runs-on: self-hosted` targets any self-hosted runner
- `runs-on: [self-hosted, linux, my-label]` targets specific ones
